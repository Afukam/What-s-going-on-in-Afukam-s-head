# AWS Cowrie + Wazuh — Evidence Plan

This plan defines the evidence required to turn the current homelab into a reproducible security-operations case study. It is deliberately separate from the progress log: a planned test is not a completed test.

## Current verified baseline

As of the latest project notes (2026-11-26), Wazuh dashboard access and an active agent were observed. Cowrie-to-Wazuh ingestion, event parsing, custom detections, and alert validation remain unverified. The honeypot has only been tested through controlled client activity; it must not be described as receiving unsolicited internet traffic.

## Evidence milestones

### 1. Infrastructure and agent health

- [ ] Sanitized architecture diagram showing EC2 roles, network boundaries, security groups, and data flow.
- [ ] Wazuh agent status and manager association, with host identifiers redacted.
- [ ] Cowrie service/process status and listener details.
- [ ] Host firewall rules and relevant AWS inbound restrictions, with account IDs and public addresses removed.

### 2. Cowrie log collection

- [ ] Identify the exact Cowrie JSON log path and confirm the file is being updated.
- [ ] Confirm Wazuh is configured to monitor the correct file using an appropriate JSON log format.
- [ ] Generate a new controlled SSH test session.
- [ ] Preserve one sanitized Cowrie JSON event and its corresponding Wazuh event.
- [ ] Record timestamps/timezone and demonstrate that the event fields are searchable.
- [ ] Document any parsing differences or missing fields.

### 3. Detection engineering

For each detection, save the exact Wazuh rule or query, prerequisites, controlled test steps, expected and observed results, alert details, false-positive considerations, and limitations.

Candidate detections (only implement after confirming available fields):
- Repeated failed authentication attempts within a defined time window.
- Successful authentication following repeated failures, if the telemetry supports reliable correlation.
- Suspicious command input observed in Cowrie sessions.

Do not assume event IDs or field names. Derive them from actual captured events and Wazuh decoder output.

### 4. Investigation case study

- [ ] Build a sanitized event timeline from one controlled test.
- [ ] Explain what the honeypot recorded and what it did not establish.
- [ ] Map observed behaviour to MITRE ATT&CK only where supported.
- [ ] Record analyst conclusions, confidence, and recommended defensive actions.
- [ ] Include limitations and alternative explanations.

## Safe publication checklist

- Remove AWS account IDs, public IPs, access keys, tokens, private keys, credentials, personal usernames, and sensitive hostnames.
- Do not publish raw configuration files if they contain secrets or network details that expose the lab.
- Use synthetic labels such as `honeypot-01` and `manager-01` in diagrams and reports.
- Keep only the minimum event fields needed to demonstrate the investigation.
- Never publish evidence that implies unsolicited external attacker activity when the event was generated by your own test client.
